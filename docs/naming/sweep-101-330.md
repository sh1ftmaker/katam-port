# Room survey: ids 101–330, and what their object records mean

**Status:** review document. Nothing has been renamed. Every naming claim carries a `file:line`
citation into `/home/agent-tom/Desktop/katam` (read-only) plus a measurement taken from
`baserom.gba` through `tools/room_export.py`. Run artefacts are in `build/sweep-a/`.

## Summary

I warped into a stratified sample of 26 of the 105 rooms whose ids fall in 101–330, spread across
all nine `songIdx` values in the range, across room sizes from 208 to 1768 collision cells, and
across object counts from 1 to 28. **The live half of this exercise mostly failed, and the failure
is the finding: a large fraction of the sample does not finish after the warp.** A healthy warp
completes 1500 frames in about 4 seconds and its collision grid matches the static reconstruction
byte for byte; a bad one reaches the warp frame and then stops advancing forever. I confirmed the
harness itself is fine by reproducing the documented-good case (`WARP=1320:804:2:5`) in this same
build: 4 seconds, `rc=0`, zero port diagnostics, *all 793 collision bytes match the running game*.
I also established one thing the known-issue investigation can use: **the hang is a property of the
room, not of the cell.** Room 300 hangs at its `--spawn` cell (13,18), at an open standing cell
(3,17), and at a ledge cell (12,2) — three different cells, same stall at the same frame. And
`tools/room_export.py --spawn` recommends cell (56,3) for room 804, which is one of the two cells
the known issue names as hanging, so the tool's own recommendation is not a safety oracle.

The static half succeeded, and it is where the lasting value is. Reading the 1,343 object records
in rooms 101–330 (and 3,476 ROM-wide as a control) against the constructors in `src/` resolves
**most of the generic `struct Object` header**: `unk1` is the record stride, `unk2`/`unk3` are a
despawn-flag *space selector* and *bit index* into three bitmaps of three different lifetimes,
`unk4` is an index into a per-room 16-entry `u32` register file that objects increment when
defeated, `unk5` bit 0 makes an object spawn at room load instead of when the camera nears it, and
`unk1A`/`unk1C`/`unk1E`/`unk20` are a signed pixel offset plus a size — one rectangle, spelled the
same way in five unrelated source files. Three fields (`unkA`, `unkB`, `unkD`) are `0xFF` in all
3,476 records in the ROM and are not parameters at all. Per-type, the chest record decodes
completely (`unk11` is the treasure id, `subtype1` is the contents, in range-encoded categories)
and the object spawner and scroll lock decode nearly completely.

Every one of the 95 object types placed in 101–330 already has a named constant in
`build/port-src/include/constants/object_types.h`. There are no unnamed types in this range.

## 3. The generic `struct Object` header

`struct Object` is 36 bytes (`include/data.h:250`). Every record in the ROM is exactly 36 bytes and
every record's `unk1` is 36 — measured on all 3,476 records — so the variable-stride mechanism in
the walker is real code that retail data never exercises.

### 3.1 `unk1` → `recordSize` (stride). Confidence: **high**

The object-list walk is `for (; obj->unk1 != 0; obj = (void *)obj + obj->unk1)` —
`src/code_080023A4.c:5890`, and again at `:5947` and `:6007`. The loop terminates on a zero `unk1`,
not on a count. So `unk1` is simultaneously the terminator and the stride.

*Measurement:* `unk1 == 36 == sizeof(struct Object)` in 3,476 of 3,476 ROM records.

*Against / unresolved:* nothing contradicts this; the only caveat is that it is a *capability*
statement — a custom record could legally be a different size and the engine would follow it.

### 3.2 `spawnTable` → constructor-table selector. Confidence: **high**

`switch (obj->spawnTable) { case 1: gSpawnFuncTable1[obj->type](obj, playerId); case 2:
gSpawnFuncTable2[obj->type](obj, playerId); }` — `src/code_080023A4.c:5981-5990`, repeated at
`:6041-6050` and `:6122-6129`.

*Measurement:* `spawnTable == 1` in **3,476 of 3,476** records ROM-wide. **`gSpawnFuncTable2`
(`src/code_080023A4.c:447`) is never selected by level data anywhere in the game.** It is reachable
only through `CreateObjTemplateAndObj` (`include/object.h:112`), whose call sites all pass 1 as
well. That is worth recording: a randomizer or editor that writes `spawnTable = 2` is entering
code that the retail ROM never enters.

### 3.3 `unkA`, `unkB`, `unkD` → not parameters. Confidence: **high**

All three are `0xFF` in **3,476 of 3,476** records ROM-wide. `CreateObjTemplateAndObj`
(`include/object.h:112-148`) does not assign any of them, so a dynamically built template leaves
them at whatever the reused slot held. No `src/` site reads `object->unkA`, `object->unkB` or
`object->unkD`.

*Against / unresolved:* `unkD` sits immediately after `type`, so `0xFF` may be padding that a tool
should preserve rather than a field. Saying "not a parameter" is safe; saying "unused" is not — I
did not audit `asm/`.

### 3.4 `unk2` → despawn-flag **space**, `unk3` → despawn-flag **bit index**. Confidence: **high**

This is the most useful pair in the header, and it is decided by one function:

```c
u32 sub_080027E8(u32 arg0, u16 arg1, u8 arg2)            /* src/code_080023A4.c:1426 */
{
    switch (arg0) {
        case 0: return gUnk_02023358[arg2][arg1 / 8] >> (arg1 & 7) & 1;
        case 1: return gUnk_02023368[arg1 / 8]       >> (arg1 & 7) & 1;
        case 2: return gUnk_02028BF0[arg1 / 8]       >> (arg1 & 7) & 1;
        default: return 0;
    }
}
```

and it is called in exactly one shape, three times, always as the first thing the spawn loop does:

```c
if (sub_080027E8(obj->unk2, obj->unk3, levelInfo->unk65E) != 0)
    continue;                       /* src/code_080023A4.c:5893, :5950, :6010 */
```

So `unk2` picks *which* bitmap and `unk3` is the *bit* in it; a set bit means **do not spawn this
object**. The matching setter is `sub_08001678(space, index, roomSlot, value)`,
`src/code_080023A4.c:687-713`, with the identical three-way switch.

The three bitmaps have three different lifetimes, and that is what makes the field worth naming:

| `unk2` | bitmap | declared | cleared by | scope |
|---|---|---|---|---|
| 0 | `gUnk_02023358[slot][4]` | `include/data.h:690` | `wip/code.c:436`, on every room load | **per room slot**, 32 bits |
| 1 | `gUnk_02023368[0x20]` | `include/data.h:691` | `sub_080027A8` — called from `wip/code.c:54`, `src/warp_star.c:2685`, `src/kirby.c:10744` | **per area**, 256 bits |
| 2 | `gUnk_02028BF0[0x20]` | `include/data.h:702` | `sub_080027C8` — called only from `src/save.c:241` | **per save file**, 256 bits; it is a member of `gWorldProps` (`src/save.c:21`) and is written to SRAM |

*Measurement, ROM-wide, and it fits the declared sizes exactly:*

| | |
|---|---|
| `unk2 == 0` | 3,077 records, `unk3` in **0..28** — fits 32 bits |
| `unk2 == 1` | 399 records, `unk3` in **0..255** — fits 256 bits, does **not** fit 32 |
| `unk2 == 2` | **0 records** — the save-persistent space is supported by code but unused by level data |

The `unk2 == 1` population is exactly the consumables: `OBJ_BATTERY`, `OBJ_POP_SODA`,
`OBJ_SMALL_FOOD`, `OBJ_MEAT`, `OBJ_TOMATO`, `OBJ_1UP`, `OBJ_COOKIN`, `OBJ_INVINCIBLE_CANDY`. That
is precisely the set that must stay collected while you walk around an area but come back when you
leave it — which is what "cleared on area transition and on warp star" means.

Two further measurements support the reading rather than merely being consistent with it:

- **No room contains two objects with the same `(unk2, unk3)`** — 0 collisions in 105 of 105 rooms
  in range for both spaces. A shared bit would despawn two objects at once.
- The `unk2 == 1` ids fall into **contiguous per-area blocks**: 45..81, 82..105, 129..201,
  135..148, 212..232. Grouping the whole ROM by `songIdx` gives 27 duplicate ids out of 399, all
  inside the two song values that are shared by more than one area. An id space allocated
  per-area is what produces disjoint blocks; a global one would not.

**The sentinel.** `(unk2 == 0, unk3 == 31)` means "no flag". Bit 31 is the top bit of the 32-bit
per-room bitmap, and:

- every dynamically created template passes exactly `unk2 = 0, unk3 = 31` —
  `src/chest.c` popup spawn, `src/object.c:451`, and the `0x1F` argument in
  `src/object_spawner.c:83`;
- the defeat handler excludes it: `if (r4->object && !ObjType43To52(r4) && (r4->object->unk2 ||
  r4->object->unk3 != 31)) ++*sub_08002888(...)` — `src/object.c:1277-1279` and `:1474-1476`.

*Measurement:* no level-data record in the ROM uses `(0, 31)`; the maximum `unk3` for `unk2 == 0`
is 28. The sentinel is reserved and level data respects the reservation.

*Against / unresolved:* the name "despawn flag" describes the *effect* at the spawn site. The bit
is also what `sub_08001678` sets on collection/defeat, so "already dealt with" would be an equally
accurate reading; I have no site that distinguishes them.

### 3.5 `unk4` → per-room register index. Confidence: **high**

```c
u32 *sub_08002888(enum SUB_08002888_ENUM arg0, u8 index, u8 subindex)   /* :1453 */
{
    case SUB_08002888_ENUM_UNK_1: return gUnk_02023388[subindex] + index;
    ...
}
```

`gUnk_02023388[][16]` (`include/data.h:685`) is a `u32[16]` per room slot, zeroed on every room
load (`wip/code.c:437`, `CpuFill32(0, gUnk_02023388[levelInfo->unk65E], 0x40)` — 0x40 bytes = 16
words). `obj->unk4` is always the `index` argument:

- **written** — `++*sub_08002888(SUB_08002888_ENUM_UNK_1, r4->object->unk4, ...)` on object defeat,
  `src/object.c:1279` and `:1476`; also `src/shadow_kirby.c:105-106`;
- **written** — `*sub_08002888(..., lavaWall->object->unk4, ...) = 1`, `src/lava_wall.c:50`;
- **read as a gate** — `src/jack.c:61, 91, 241, 268, 290`; `src/lava_wall.c:58`;
  `src/scroll_lock.c:310-312, 373, 431, 475, 525, 584`.

So a room's objects share a little bank of counters: enemies increment the register named by their
`unk4`, and gates, lava walls and scroll locks watch it. That is the engine's "defeat all the
enemies here and the wall opens" mechanism, and it is entirely data-driven.

*Measurement:* `unk4` is 0 (meaning "no register", explicitly checked as `if (obj->unk4)` at
`src/scroll_lock.c:310` and `src/shadow_kirby.c:105`) in all but 75 of 1,343 records in range. The
non-zero users are exactly the controller-ish types: scroll locks, buttons, sliding doors, shadow
Kirby, cannons, mini-bosses, doors-to-hub.

*Against / unresolved:* `gUnk_02023388`'s second dimension is 16, so valid indices are 0..15, and
`src/big_small_switch.c:376` uses index 15 explicitly as a well-known slot. **In room 801 an
`OBJ_HUB_MIRROR` carries `unk4 == 18`, which is out of bounds** and would read into the next room
slot's bank. Room 801 is outside my range and I did not chase it, but it is either a genuine
engine quirk the hub relies on or evidence that the second dimension is larger than the header
says. Everything in 101–330 is ≤ 12.

### 3.6 `unk5` bit 0 → spawn at room load, ignoring the camera. Confidence: **high**

`CreateLevelObjects` (`src/code_080023A4.c:5876`) walks the object list and, for each record that
survives the despawn-flag test:

```c
if ((obj->unk5 & 1) == 0) {
    ...  /* skip unless obj is within ~0x16 x 0x11 cells of this player's viewport,
            and not too close to another player's viewport */
}
CreateObject(playerId, obj);      /* src/code_080023A4.c:5897-5934 */
```

With bit 0 set the whole proximity test is skipped and the object is created unconditionally.

*Measurement:* 235 of 3,476 records ROM-wide have `unk5 != 0`, and the only value ever used is 1.
In range the users are `OBJ_SCROLL_LOCK` (16), `OBJ_WIND_EFFECT` (6), `OBJ_BIG_BUTTON` (6),
`OBJ_VERTICAL_SLIDING_DOOR` (5), `OBJ_SHADOW_KIRBY` (4), `OBJ_SMALL_BUTTON` (4), `OBJ_BOX_BOXER`,
`OBJ_CANNON`, `OBJ_LAVA_WALL`, `OBJ_STAR_PLATFORM`, `OBJ_TRIGGERABLE_WALL`, `OBJ_BIG_CHEST`, and
every boss in the range (`OBJ_WIZ`, `OBJ_BONKERS`, `OBJ_MR_FROSTY`, `OBJ_PHAN_PHAN`, `OBJ_BOXY`,
`OBJ_DARK_META_KNIGHT_W8`). That is the set of objects that must exist before you can see them —
camera controllers, room logic, and bosses.

*Against / unresolved:* only bit 0 is ever tested and only value 1 ever appears, so bits 1–7 are
unconstrained by both code and data.

### 3.7 `unk1A`, `unk1C`, `unk1E`, `unk20` → a rectangle: offset x, offset y, width, height.
Confidence: **high**

Five unrelated files spell the same four lines:

```c
rect[0] = obj->unk1A;                 /* src/lava_wall.c:39-42          */
rect[1] = obj->unk1C;                 /* src/star_stone_block.c:424-427 */
rect[2] = rect[0] + obj->unk1E;       /* src/object_spawner.c:160-163   */
rect[3] = rect[1] + obj->unk20;       /* src/star_platform.c:42-45      */
```

and `src/ability_objects.c:481-493` uses the same decomposition per direction: `y + unk1C` for the
top edge, `x + unk1A + unk1E` for the right, `y + unk1C + unk20` for the bottom, `x + unk1A` for
the left. `src/star_platform.c:26-29` builds its travel extent the same way. Two files test the
quadruple as a unit for "is a region configured at all": `src/batty.c:317` and
`src/golem.c:271-274`.

`src/object_spawner.c:160` and `src/star_platform.c:42` add the object's own `x`/`y` first, so the
pair is a **signed offset from the object**, and `unk1E`/`unk20` are an unsigned **size**, both in
pixels. `struct Object` already declares `unk1A`/`unk1C` as `s16` and `unk1E`/`unk20` as `u16`
(`include/data.h:266-269`), which agrees.

*Measurement:* `OBJ_CPU_KIRBY_TRIGGER` in range carries `(-8, -8, 16, 16)` three times,
`(-16, -16, 32, 32)` and `(-24, -24, 64, 48)` — centred boxes, which is what a trigger volume
should look like. `OBJ_WIND_EFFECT` carries tall thin regions (e.g. `unk20 = 816` px in a room
848 px high). All values in range are multiples of 8.

*Against / unresolved:* **`OBJ_SCROLL_LOCK` carries a full rectangle in these four fields and
`src/scroll_lock.c` never reads any of them.** I compared it against the camera rectangle the
scroll lock *does* use (§4.1) for all 52 scroll locks in the ROM: the two agree to within one or
two cells but are equal in only 1 of 52. So it is a related-but-different rectangle — plausibly
editor metadata or a trigger volume for a mode that shipped unused — and I cannot say which.

### 3.8 `subtype2` → the runtime `subtype`. Confidence: **high**

`InitObject` copies it: `arg0->subtype = arg1->subtype2;` — `src/object.c:2043` (`InitObject`, the line after
`arg0->object = arg1;` at `:2042`). So the template field named `subtype2` is the
source of the runtime field already named `subtype` on `struct Object2`, which is consulted
generically (e.g. `src/waddle_dee.c:401`). The name asymmetry is the confusing part, not the
meaning.

The same function establishes that **`x` and `y` are pixel coordinates**: `arg0->base.x = arg1->x * 0x100` (`src/object.c:2031`), and the spawn loop compares `obj->x >> 4` against viewport values taken as
`viewportPosition.x >> 0xC` — 16 px per cell, 0x1000 sub-units per cell.

### 3.9 `subtype1` → a per-type behaviour variant. Confidence: **medium-high**

Read only through `obj->subtype1` / `obj->object->subtype1`, and every consumer is a `switch`
inside one type's constructor: `src/waddle_dee.c:53` and `:75` (five movement patterns),
`src/bronto_burt.c:135` and `:172`, `src/gordo.c:37` (four), `src/blipper.c:620, 666, 747, 827,
891, 1034`. So it is a parameter, but its *enum* is private to each type; there is no cross-type
meaning to name.

*Measurement:* 27 distinct values in range, but per type the sets are tiny and consistent —
`OBJ_WADDLE_DOO` uses only {0, 3}; `OBJ_FLAMER` only {0, 1} with 1 in 18 of 23 placements;
`OBJ_GORDO` only {1, 2}; `OBJ_TWISTER` and `OBJ_BOXIN` split 50/50 between two values.

*Against / unresolved:* one `OBJ_WADDLE_DEE_1` in range carries `subtype1 == 5`, and
`src/waddle_dee.c:53` has cases 0–4 only, so it falls to `default` and behaves as 0. Either the
value is a level-data mistake or there is a reader I did not find.

### 3.10 `unkF` → sprite-palette variant. Confidence: **medium**

Two sites, both passing it as the second argument of `sub_0803DFAC`:

```c
sub_0803DFAC(v3, obj->object->unkF);      /* src/object.c:451             */
sub_0803DFAC(unk8, obj2->object->unkF);   /* src/code_0806F780.c:8777     */
```

where `v3` / `unk8` is `gUnk_08351648[type].unk8`, the type descriptor's palette id. And
`u8 sub_0803DFAC(u16 r2, u8 r6)` (`src/kirby.c:5774`) forwards `r6` to `SpriteSomething(...,
r2 & 0xFFF, r6, ...)` — the *variant* slot. **Every other call site in the game passes 0.**

*Measurement:* non-zero in only 81 of 3,476 records, concentrated in `OBJ_SMALL_CHEST` (34),
`OBJ_DOOR_TO_HUB` (22), `OBJ_BIG_CHEST` (15), `OBJ_TRIGGERABLE_WALL` (5). Values run 4..38.

This also **contradicts the existing comment.** `include/data.h:255` reads `u8 unkF; // Foreground
boolean?`. It takes 13 distinct non-zero values on chests alone; it is not a boolean.

*Against / unresolved:* on chests, `unkF` is *not* the item id — the popup derives its own sprite
and variant from `subtype1` (`src/chest.c:178-230`), so `unkF` is a second, independent index. It
correlates with `subtype1` (for spray-paint chests, `unkF == subtype1 - 16` exactly) but the
mapping is not uniform across the other categories, so I can say it is a variant index and not
what enumerates it.

### 3.11 Fields I could not pin down

`unk11`, `unk12`, `unk14`, `unk16`, `unk18` and `unk22` are **per-type parameter words**. There is
no generic reader for any of them; every consumer is one object's constructor, and the meanings do
not transfer between types. `unk22` in particular is a *bitfield whose bits mean different things
per type* — compare `src/chest.c:33` (bit 0 = facing), `src/object_spawner.c:103` (bit 0 = use the
explicit trigger rect), `src/scroll_lock.c:87` (bits 0–1 = lock mode), `src/special_doors.c:330`
and `src/mirror_door.c:120` (bit 8 = alternate door marker sprite). Naming `unk22` generically
would be the exact mistake this document is supposed to avoid.

## 4. Per-type decodings

### 4.1 `OBJ_SCROLL_LOCK` (0x77) — the camera lock rectangle. Confidence: **high**

`gSpawnFuncTable1[0x77]` is `CreateScrollLock` (`data/object.s`), and `sub_0811C9D4`
(`src/scroll_lock.c:81`) reads the template directly:

```c
p->unk8  = (obj->unk14 & 0xFF00) << 4;                     /* :141 */
p->unkC  = (obj->unk14 & 0x00FF) << 12;
p->unk10 = p->unk8 + ((obj->unk12 & 0xFF00) << 4);
p->unk14 = p->unkC + ((obj->unk12 & 0x00FF) << 12);
```

`sub_0811C7D0` (`:23-49`) then writes those four into `gCurLevelInfo[player].unk_S32Vec2_7C`,
`unk_S32Vec2_84`, `unkA0..unkAC` — the camera bounds. The unit is 0x1000 per 16-pixel cell: the
same function's clamps use `0xF800` (15.5 cells = 248 px) and `0xA000` (10 cells = 160 px) against
the viewport, i.e. one GBA screen. So `<< 12` on a byte means *that byte is a cell coordinate*.

Therefore:

| field | reading |
|---|---|
| `unk14` high byte | lock rect **left**, in 16-px cells |
| `unk14` low byte | lock rect **top**, in 16-px cells |
| `unk12` high byte | lock rect **width**, in cells |
| `unk12` low byte | lock rect **height**, in cells |

*Measurement, and this is the part that settles it:* of the 52 scroll locks in the whole ROM,
**47 have `unk12 == 0x0F0A`** — 15 cells by 10 cells — **exactly 240×160 pixels, the GBA screen.**
The other four values are `0x0F0D` (240×208, ×3), `0x0F18` (240×384) and `0x1E0A` (480×160). A
field that lands on the screen dimensions in 47 of 52 samples under a reading derived from
unrelated shift arithmetic is not a coincidence.

`unk22` on a scroll lock is a mode word: `switch (obj->unk22 & 3)` at `:87` picks one of four
allocation/behaviour variants, bit 2 shifts all four bounds by `0x800` (half a cell) at `:145` and
`:210`, and bit 3 is tested at `:611`. All 18 in range have `unk22 & 3 == 2`; the raw values are
2, 6, 22 and 14. `unk4` is the room register (§3.5) and `unk16`/`unk18` are read at `:169-172` and
`:234-237` but are zero in every placement in range, so I have code for them and no data.

### 4.2 `OBJ_SMALL_CHEST` (0x80) / `OBJ_BIG_CHEST` (0x81) — completely decoded. Confidence: **high**

`CreateChest` (`src/chest.c:22`):

```c
chest2->unkE0 = arg0->subtype1;      /* :30 */
chest2->unkE2 = arg0->unk11;         /* :31 */
...
if (HasChest(chest->unkE2)) ...      /* :47 */
```

**`unk11` is the chest id**, the argument of `HasChest`/`CollectChest`
(`src/treasures.c:24, 27-29`), which index `gTreasures.chestFields` — part of `gWorldProps` and
therefore saved (`src/save.c:24`).

*Measurement:* there are **84 chest objects in the ROM and their `unk11` values are exactly
0..83, each used once.** A dense bijection is what a save-bitfield index must be. It also matches
independently: `docs/ROOM-FORMAT.md` §7 counts **84 chest entries** in the progress table, derived
from an entirely different table by an entirely different walk.

**`subtype1` is the contents**, range-encoded by category — `src/chest.c:114-137` and
`src/chest.c:301-330`:

| `subtype1` | contents |
|---|---|
| 0 | 1UP |
| 1 | Invincible Candy |
| 2 | Maxim Tomato |
| 3 | Meat |
| 4 | Pop Soda |
| 5 | Small Food |
| 6 | Vitality (max-HP upgrade) — `CollectVitality()`, `maxHp = NumVitalitiesCollected() + 6` |
| 0x0A..0x13 | big-chest treasure, index `subtype1 - 0x0A` |
| 0x14..0x21 | spray paint, index `subtype1 - 0x14` |
| 0x28..0x32 | music player / sheet, index `subtype1 - 0x28` |
| 0x63 | opens with no award |

*Measurement:* the ROM-wide histogram lands inside those ranges with no strays, and **every
treasure index appears exactly once**: 10 values in 0x0A..0x13, 14 in 0x14..0x21, 11 in
0x28..0x32, all with count 1, while the consumable values 0..6 repeat freely (18 chests give a
1UP). 10 + 14 + 11 = 35 unique treasures, and the rest of the 84 are consumables, vitality and the
four `0x63` chests.

`unk22` bit 0 flips the chest's facing (`src/chest.c:33-38`). `unk11` on a chest is the id;
note that `unk11` means something entirely different on `OBJ_BIG_BUTTON`
(`src/big_small_switch.c:377`, a value written into room register 15).

### 4.3 `OBJ_OBJECT_SPAWNER` (0x73). Confidence: **high**

`src/object_spawner.c:82-98`:

```c
created = CreateObjTemplateAndObj(..., x->obj2.object->x, x->obj2.object->y, 0, 0x1F, 0, 0,
    (u8)x->obj2.object->unk14,          /* type       */
    x->obj2.object->subtype1, 0,
    x->obj2.object->subtype2,
    spawnFlag,
    x->obj2.object->unk1A, x->obj2.object->unk1C,
    x->obj2.object->unk1E, x->obj2.object->unk20, 0, 0, 0, 0, 0);
n = x->obj2.object->unk14 >> 8;         /* :90: bound of the alive-slot array */
```

| field | reading |
|---|---|
| `unk14` low byte | **object type to spawn** |
| `unk14` high byte | **maximum simultaneously alive** |
| `unk12` | **respawn delay in frames** — `if (x2->spawnCounter >= obj->unk12)`, `:65-66` |
| `subtype1`, `subtype2` | passed through to the spawned object verbatim |
| `unk1A/1C/1E/20` | passed through as the spawned object's region (§3.7) |
| `unk22` bit 0 | use the explicit region as the Kirby-proximity trigger instead of a default `(-8,-24)..(+8,-8)` box — `:159-169` |

*Measurement:* all 16 spawners in range have `unk14 >> 8 == 1` (one alive at a time), and the low
bytes are 0x02, 0x07, 0x08, 0x0F, 0x14, 0x27, 0x29, 0x2A — `OBJ_BLIPPER`, `OBJ_SNOOTER_1`,
`OBJ_CHIP`, `OBJ_LEAP`, `OBJ_HOT_HEAD`, `OBJ_MINNY`, `OBJ_HEAVY_KNIGHT`, `OBJ_GIANT_ROCKY`. Every
one is a real, plausible enemy type — that is the check that makes the "low byte is a type" reading
more than arithmetic. `unk12` takes only {0, 60, 90, 120}: 0, 1, 1.5 and 2 seconds at 60 Hz.

### 4.4 `OBJ_DOOR` (0x6F, `CreateMirrorDoor`) and `OBJ_AREA_DOOR` (0x99) — `unk22` bit 8.
Confidence: **medium-high**

`src/mirror_door.c:120, 130, 157` and `src/special_doors.c:330` all branch on
`object->unk22 & 0x100` to choose the door's marker sprite: with the bit, sprite `0x294`
variant 9/0xA; without it, `0x294` variant 2/3 or sprite `0x2CF`. So bit 8 selects an **alternate
door-marker appearance**.

*Measurement:* `unk22` on `OBJ_DOOR` in range takes exactly two values, 0 (100 placements) and
0x100 (79). A field with one live bit and a near-even split is a per-door appearance switch, which
is what the code says it is. One `OBJ_AREA_DOOR` in range also sets it.

*Against / unresolved:* I did not determine what visually distinguishes the two markers, so
"alternate" is as specific as the evidence gets. Do not name it "mirror door" without checking a
frame.

### 4.5 `OBJ_FLAME_COLUMN` (0x7C). Confidence: **medium**

`src/flame_column.c:77-95`: `unk12` gates a per-step counter, `unk14` is the extension length
(`unkB4` counts up to it and is clamped to `unk14 - 1`), `unk16` is the dwell while retracted and
`unk18` the dwell while extended, both compared against a frame counter.

*Measurement:* in range `unk14 ∈ {3, 4}`, `unk12 ∈ {2, 3, 30}`, and `unk16`/`unk18` ∈ {30, 60,
100, 101, 120, 180} — i.e. half-second multiples at 60 Hz, which is what dwell timers look like
and what extension lengths do not.

## 5. What I could not determine

- **Why some rooms hang after a warp.** I established it is not the cell (three cells, one room,
  same stall) and not the harness (the documented-good case reproduces in this build in 4 seconds
  with a passing collision check). I did not find what distinguishes a hanging room from a working
  one, and per the task I did not chase it. One concrete item for whoever does:
  `tools/room_export.py --spawn` recommends cell **(56,3)** for room 804, which the known issue
  names as a hanging cell — so the tool's "safe warp cell" is not currently a safety oracle, and a
  sweep that trusts it will hang more than a sweep that hand-picks.
- **The collision value at the arrival cell does not predict the hang.** Room 804 cell (2,5)
  (works) and (3,5) (hangs) are adjacent cells with the *identical* metatile index 13, attribute
  `0x00000200`, solid, non-door, solid below. That rules out one obvious hypothesis.
- **`OBJ_SCROLL_LOCK`'s `unk1A/1C/1E/20`.** A well-formed rectangle that `src/scroll_lock.c` never
  reads, close to but not equal to the camera rectangle it does read (1 exact match in 52).
- **`unk16` and `unk18` on the scroll lock.** `src/scroll_lock.c:169-172` reads them as a
  high-nibble-shifted pair plus a sign test, but they are zero in every scroll lock in 101–330, so
  there is code and no data to check it against.
- **`unkF`'s enumeration.** Established as the palette variant argument; not established what
  indexes it, since on chests it is neither the item id nor the chest id.
- **`unk4 == 18` on room 801's `OBJ_HUB_MIRROR`**, against a declared bank of 16 registers.
  Outside my range, unresolved, and it means either the header's `[16]` is wrong or the hub relies
  on reading the adjacent room slot's bank.
- **`unk2 == 2`.** The save-persistent despawn bitmap is fully implemented in
  `sub_080027E8`/`sub_08001678` and never selected by any of the 3,476 records in the ROM. Whether
  anything reaches it through a dynamically built template, I did not check.
