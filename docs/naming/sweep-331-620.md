# Room sweep: ids 331–620

A stratified sample of **27 of the 99 rooms** whose ids fall in 331–620, spread
deliberately across size (256×208 up to 2176×208 and 256×1648), object count
(1 to 29) and `songIdx` (0, 4, 8, 10, 11, 37). **All 27 load, all 27 pass the
collision check — 27,876 collision bytes verified against the running game —
and all 27 produce zero port diagnostics.** That includes **room 417 (Crazy
Hand)**, the first boss room ever observed loading in this port: it loads
clean, and Kirby's HP falls 6→0 over the following 60 seconds of game time,
which is direct evidence that the boss is not merely present but attacking.
The range also contains a second, previously unreported boss room — **516,
Moley** — which loads clean but whose fight I could *not* confirm. On the
static side, cross-referencing the range's 1,261 object records against
`~/Desktop/katam/src/` turns several `unk` fields into parameters with named
meanings, the strongest being `unk1A/unk1C/unk1E/unk20` (a trigger rectangle,
proven by the game's own point-in-rect helper), `unk2`/`unk3` (a two-namespace
"already consumed" bit index), `unk5` bit 0 (spawn regardless of camera), and
the `OBJ_OBJECT_SPAWNER` and `OBJ_SCROLL_LOCK` parameter blocks, which decode
into values that are self-evidently right (spawner `unk14` low byte names a
valid enemy type in 37 of 37 placements; scroll-lock `unk12` is exactly one
GBA screen in 47 of 52).

**An important caveat on process.** My first pass ran against the pre-01:22
build and every one of 38 warp attempts across 34 rooms hung, the sole
exception being room 804 at (2,5). That measurement is superseded — the cause
was the unterminated door-table walk in `sub_08002C18`, fixed in
`platform/warp.c` — and every runtime number below comes from a re-run against
the fixed build. The one durable thing worth keeping from the broken pass is
recorded in "What I could not determine".

## 2. The boss rooms

### 417 — Crazy Hand: loads, and the fight runs

Room 417 is 256×208 px (16×13 cells), song 37, and holds exactly **one object**:

```
type 71 = 0x47 = OBJ_CRAZY_HAND_1   at (216, 72)
  unk1A=-208  unk1C=-64  unk1E=240  unk20=152
  unk2=0 unk3=0 unk4=0 unk5=1  subtype1=0 subtype2=0  everything else 0
```

All 208 collision bytes match the running game. Beyond loading:

- Task population rises from 18 pre-warp to 26 within 120 frames of arrival,
  then oscillates 19–29 for the remaining 3,600 frames of a 5,000-frame run —
  objects being created and destroyed repeatedly, which is what a boss doing
  things looks like. A room that merely loaded would settle.
- **`gKirbys[0].hp` (`s8` at `0x02020FE0`, from `linker.ld:16` plus
  `offsetof(struct Kirby, hp) == 256` asserted at `platform/port/gba_layout.h:696`)
  falls 6 → 5 → 4 → 3 → 2 → 1 → 0** over 2,400 frames after the warp, sampled
  every 240 frames. `maxHp` in the adjacent byte stays 6 throughout.
- Zero diagnostics across the whole 5,000-frame run.

Kirby cannot lose HP to nothing. Crazy Hand is spawning, acting and dealing
damage. This is the first boss fight observed running in this port.

The object's rectangle is worth reading out: offset from the object's own
position it spans x ∈ [8, 248], y ∈ [8, 160] in a 256×208 room — i.e. very
nearly the entire playfield, which is what a "start the fight the moment the
player is in the arena" trigger should look like. See §3.1 for why that
rectangle is a rectangle.

### 516 — Moley: loads clean, fight unconfirmed

Not previously reported anywhere in `docs/`. Room 516 is 992×368 px, song 37,
and holds three objects:

```
type 0x77 OBJ_SCROLL_LOCK  at (536,256)  rect (-56,-64, 520×128)
type 0x4A OBJ_MOLEY        at (592,264)  rect (-112,-72, 256×128)
type 0x77 OBJ_SCROLL_LOCK  at (864,216)  rect (-128,-88, 272×160)
```

All 1,426 collision bytes match. Task count rises 18 → 25 after the warp, and
diagnostics stay at 0 over 4,000 frames. But **Kirby's HP stayed at 6 for the
whole run, from two different spawn points** — the door arrival cell (15,1),
and (35,14), which I picked because it is inside Moley's trigger rectangle
(x ∈ [480,736], y ∈ [192,320]). So I can say room 516 loads correctly and I
cannot say the Moley fight starts. Moley is a burrowing boss that surfaces
only intermittently, so "no damage in 60 s while holding RIGHT" is weak
evidence either way. Treat this as open.

## 3. Object fields: what the data plus the source support

1,261 object records across the 99 rooms in the range; 3,476 across all 286
rooms. Where a claim generalises I give the all-286 number, because a field
that is constant across 1,261 samples and varies across 3,476 is not constant.

Every type byte placed in 331–620 — **85 distinct types** — has a real name in
`build/port-src/include/constants/object_types.h`. **None** map to an
`OBJ_UNKNOWN_*` or `OBJ_EMPTY_*` constant, and none fall outside the table. So
the "any object type with no named constant" question has a clean negative
answer for this range. (The enum's alignment is independently confirmed by this
sweep: room 417 is Crazy Hand by prior knowledge and its only object is type
0x47 = `OBJ_CRAZY_HAND_1`.)

### 3.1 `unk1A`, `unk1C`, `unk1E`, `unk20` — a trigger rectangle. **High confidence.**

Proposed: `triggerOffsetX`, `triggerOffsetY`, `triggerWidth`, `triggerHeight`.

The decisive site is the game's own helper, in C:

```c
/* ~/Desktop/katam/wip/code_08032E98.c:944 */
u8 sub_08039430(struct ObjectBase *obj, s32 x, s32 y, s16 offX, s16 offY, u16 w, u16 h)
{
    s32 x1 = (x >> 8) + offX;
    s32 y1 = (y >> 8) + offY;
    ...
}
```

and the macro that feeds it, which passes exactly these four fields in exactly
this order:

```c
/* ~/Desktop/katam/include/object.h:368 */
#define Macro_08039430_1(objBase, obj2) sub_08039430(objBase, \
    (obj2)->base.x, (obj2)->base.y, \
    (obj2)->object->unk1A, (obj2)->object->unk1C, \
    (obj2)->object->unk1E, (obj2)->object->unk20)
```

So the rect's top-left is the object's own position plus (`unk1A`, `unk1C`),
and (`unk1E`, `unk20`) are its width and height, all in pixels. Two unrelated
files build the same rect by hand with the same formula:

- `~/Desktop/katam/src/star_platform.c:42-45`
- `~/Desktop/katam/src/object_spawner.c:160-163`

and `~/Desktop/katam/src/master_hand.c:162`, `src/wiz.c:158`,
`src/moley.c:157`, `src/kracko.c:290`, `src/dark_meta_knight.c:213`,
`src/king_golem.c:93`, `src/golem.c:276`, `src/shadow_kirby.c:116`,
`src/batty.c:318` all gate their boss on `Macro_08039430_1` — i.e. "is a Kirby
inside my rectangle".

Measured: 194 of 3,476 objects ROM-wide have a non-zero rect, spread over 40
types, and those types are overwhelmingly bosses, mid-bosses, spawners and
moving platforms — the things that need an activation or travel region.
`src/star_platform.c:26-29` reads the same four fields as a moving platform's
travel bounds (`plat->unkB4 = unk1A + 8` … `unkB8 = unkB4 + unk1E - 0x10`),
which is a *different* use of the same rectangle, so "trigger" is slightly too
narrow as a name; `activationRect`/`regionX/Y/W/H` may be better.

**Against / unresolved.** `src/ability_objects.c:319-321` reads `unk1A`,
`unk1C` and `unk1E` as `spawnLocation.x`, `spawnLocation.y` and `roomId` — a
completely different meaning, for that one object type. So this is a
*conventional* layout that most consumers honour, not a struct-level guarantee.
Any name given to these fields must be understood as "what nearly everything
does with them", and a tool that rewrites them cannot assume it.

### 3.2 `unk2` and `unk3` — namespace and bit index of a "do not respawn" flag. **High confidence.**

Proposed: `unk2` → `despawnFlagSpace`, `unk3` → `despawnFlagIndex`.

The object-creation loop skips an object outright when the flag is set:

```c
/* ~/Desktop/katam/src/code_080023A4.c:5893-5894 (CreateLevelObjects) */
for (; obj->unk1 != 0; obj = (void *) obj + obj->unk1) {
    if (sub_080027E8(obj->unk2, obj->unk3, levelInfo->unk65E) != 0)
        continue;
```

and the lookup is a plain bitmap select (`src/code_080023A4.c:1426`):

```c
u32 sub_080027E8(u32 arg0, u16 arg1, u8 arg2) {
    switch (arg0) {
        case 0: return gUnk_02023358[arg2][arg1 / 8] >> (arg1 & 7) & 1;  /* per room slot */
        case 1: return gUnk_02023368[arg1 / 8] >> (arg1 & 7) & 1;        /* global */
        case 2: return gUnk_02028BF0[arg1 / 8] >> (arg1 & 7) & 1;
    }
}
```

with the matching setter at `src/code_080023A4.c:688` (`sub_08001678`), called
on object teardown at `src/object.c:2092` and `src/object.c:2222` with
`(unk2, unk3)` from the same record.

The measurements line up exactly with the bitmap sizes, which is what makes
this more than a plausible reading:

| | measured over all 286 rooms | the array |
|---|---|---|
| `unk2 == 0` | 3,077 objects, `unk3` ∈ 0..**28**, never duplicated *within* a room | `gUnk_02023358[][4]` = **32 bits per room slot** (`include/data.h:690`) |
| `unk2 == 1` | 399 objects, `unk3` ∈ 0..**255**, exactly **256** distinct values | `gUnk_02023368[0x20]` = **256 bits, global** (`include/data.h:691`) |
| `unk2 == 2` | never used by level data | |

And the tightest single result: for **3,077 of 3,077** objects with `unk2 == 0`,
`unk3` equals the object's own position in its room's list among the `unk2 == 0`
objects. So the per-room flag index is simply the object's ordinal. That is not
a field a randomizer may permute independently of order.

**Against / unresolved.** The global space is *saturated*: 399 objects share
256 indices, and 143 indices are used by exactly two objects each. Collecting
one of a shared pair therefore also suppresses the other. I cannot tell whether
that is deliberate (paired items in mirrored rooms) or forced by a 256-bit
budget, and I did not test it in-game. The 11 types that use `unk2 == 1` are
0x10, 0x26, 0x5E–0x64, 0x72, 0x79 — the food/1UP/candy group plus Jack, Cookin,
the boss-challenge door and the star stone block, which is not an obviously
coherent set.

### 3.3 `unk5` bit 0 — spawn regardless of the camera. **High confidence.**

Proposed: `unk5` → `spawnFlags`, bit 0 = `SPAWN_IGNORE_CAMERA`.

Same loop, immediately after the flag check
(`~/Desktop/katam/src/code_080023A4.c:5897`):

```c
if ((obj->unk5 & 1) == 0) {
    /* ~22x17 cell window around the viewport; `continue` if the object is outside */
    ...
}
CreateObject(playerId, obj);
```

With bit 0 clear the object is only instantiated when it is near the viewport;
with bit 0 set it is instantiated at room load unconditionally. Measured: 235
of 3,476 objects ROM-wide set it, across 37 types, and they are the types you
would want to exist off-screen — bosses (0x39–0x3F, 0x47, 0x4A), scroll locks,
vertical sliding doors, big buttons, cannons.

**Against / unresolved.** Bits 1–7 of `unk5` are never set in any of the 3,476
records, so "flags" is an extrapolation from a single live bit. The correlation
with a non-zero trigger rect is real but only partial (121 of the 235), so the
two are not the same concept and neither implies the other.

### 3.4 `spawnTable` — real, and dead. **High confidence.**

`~/Desktop/katam/src/code_080023A4.c:5979-5991` switches on it to pick
`gSpawnFuncTable1[obj->type]` or `gSpawnFuncTable2[obj->type]`, so the
decompilation's existing name is accurate. But `gSpawnFuncTable2` is defined in
C at `~/Desktop/katam/src/code_080023A4.c:447` as exactly

```c
void *(*const gSpawnFuncTable2[])(const struct Object *, u8) = { NULL, NULL, NULL, NULL };
```

— four null entries. And **`spawnTable` is 1 in all 3,476 records in the ROM.**
So the second table is unreachable in retail data and would null-dispatch if
anything selected it. Worth knowing for anything that writes object records.

### 3.5 Fields that are not parameters at all. **High confidence — this is a measurement.**

Constant across **all 3,476 objects in all 286 rooms**:

| field | value | note |
|---|---|---|
| `unkA` | 255 | never varies |
| `unkB` | 255 | never varies |
| `unkD` | 255 | never varies |
| `unk1` | 36 | the record stride; the walk is `obj += obj->unk1` (`src/code_080023A4.c:5893`), so it is per-record data, but retail never uses a second size |
| `spawnTable` | 1 | see §3.4 |

Saying so is the finding. `unkA`, `unkB` and `unkD` carry no information in the
shipped game; 0xFF in three adjacent bytes reads like an unused/sentinel triple.
I did **not** find any read of `Object.unkA`, `unkB` or `unkD` in `src/`, which
is consistent but is an absence of evidence, not proof — I did not search
`asm/`.

### 3.6 `OBJ_SCROLL_LOCK` (0x77) parameter block. **High confidence on `unk12`/`unk14`, medium on the `unk22` bits.**

From `~/Desktop/katam/src/scroll_lock.c:141-144` (and the identical arithmetic
at :161-164, :206-209, :226-229):

```c
p->unk8  = (object->unk14 & 0xFF00) << 4;                    /* left   */
p->unkC  = (object->unk14 & 0x00FF) << 12;                   /* top    */
p->unk10 = p->unk8 + ((object->unk12 & 0xFF00) << 4);        /* right  */
p->unk14 = p->unkC + ((object->unk12 & 0x00FF) << 12);       /* bottom */
```

Coordinates are 16 px per unit (`<< 12` for the low byte, `<< 4` after an
implicit `<< 8` for the high byte), so:

- **`unk14` = `(cellX << 8) | cellY`** — the locked region's top-left, in 16 px cells.
- **`unk12` = `(widthCells << 8) | heightCells`** — its size, in 16 px cells.

The measurements are the confirmation, and they are hard to argue with:

- **47 of the 52 scroll locks in the ROM have `unk12 == 0x0F0A` — 15×10 cells
  = 240×160 px = exactly the GBA screen.** The other four values are
  (15,13), (15,24) and (30,10); nothing else occurs.
- Decoding `unk14` as `(cellX << 8) | cellY` puts the region's origin **inside
  the room for 17 of the 17** placements in this range. The alternative byte
  order would not.

Bits of `unk22`, all from `scroll_lock.c`:

| bit | site | effect |
|---|---|---|
| `& 3` | :87-111 | mode selector, 4 arms; picks which of `sub_0811CB44/CBB8/CD1C/CD90` runs and hence which update function is installed |
| `& 4` | :145-151, :210-216 | adds 0x800 (half a cell, 8 px) to all four edges |
| `& 8` | :611 (`ScrollLockDestroy`) | when set, do **not** restore the previous camera bounds on teardown |
| `& 0x10` | :33 (`sub_0811C7D0`) | also write the hard bounds `unk_S32Vec2_6C/74`, not just the soft ones |

**Measured, and it is a finding in itself: `unk22 & 3 == 2` in all 52
placements ROM-wide.** Modes 0, 1 and 3 ship in the code and are never used.
Modes 1 and 3 are the auto-scrolling ones — they are the only readers of
`unk16` and `unk18` (`scroll_lock.c:169-172` and :234-237, as X and Y scroll
speeds) — and correspondingly **`unk16` and `unk18` are 0 in all 52 scroll
locks in the ROM**. So for this object type those two fields are dead data,
and the auto-scroll feature is unshipped.

**Against / unresolved.** The bit meanings above are single-site readings; I
did not observe any of them at runtime. Mode 2 selecting per-player rather than
all-players behaviour (`sub_0811D508` loops players individually, `sub_0811CEF4`
requires all four to be inside) is a reading of control flow, not a test.

### 3.7 `OBJ_OBJECT_SPAWNER` (0x73) parameter block. **High confidence.**

From `~/Desktop/katam/src/object_spawner.c:28-105`:

| field | site | meaning |
|---|---|---|
| `unk14 & 0xFF` | :85 | **the object type to spawn** — passed as the type argument to `CreateObjTemplateAndObj` |
| `unk14 >> 8` | :36-38, :63, :90, :126 | **max simultaneously alive**; also sizes the child-pointer array |
| `unk12` | :65-66 | **spawn interval in frames** (`spawnCounter >= object->unk12`) |
| `unk18 >> 8` | :62 | threshold on a level counter before spawning starts |
| `unk22 & 1` | :103 | when clear, run the child-reaping pass `sub_0811BE64` |
| `unk22 & 2` | :56-58 | which of two level counters (`sub_080029E4` vs `sub_080029BC`) feeds the threshold |
| `subtype1`, `subtype2`, `unk1A`–`unk20` | :85-88 | passed straight through to the spawned object |

The confirmation is that the decode produces sense on every sample. Across all
**37** spawner placements in the ROM, `unk14 & 0xFF` is one of 0x02, 0x05,
0x07, 0x08, 0x0F, 0x14, 0x27, 0x29, 0x2A, 0x39, 0x3A, 0x3C, 0x3D, 0x3E, 0x3F —
**every one a named enemy or boss** (Blipper, Scarfy, Snooter, Chip, Leap, Hot
Head, Minny, Heavy Knight, Giant Rocky, Bonkers, Phan Phan, Box Boxer, Boxy,
Master Hand, Bombar), and never a value outside the type table. `unk14 >> 8` is
1 in all 37. `unk12` takes 0, 14, 24, 30, 40, 50, 60, 90, 120 — half-second to
two-second intervals, and in room 526 four spawners of the same enemy carry
60/50/40/30, a staircase that is obviously a difficulty ramp.

The code also does something that closes the loop on the type reading:

```c
/* object_spawner.c:33, and again at :67 */
if ((u16)((u8)obj2->object->unk14 - 0x38) <= 0x1A)   /* type in 0x38..0x52 */
```

— a different spawn animation and sound for spawned types in 0x38..0x52, which
is exactly the boss block of the type enum (`OBJ_MR_FROSTY` .. `OBJ_DARK_META_KNIGHT_W8`).
And the only spawners whose low byte falls in that window are in rooms 955,
956 and 957 — the boss-rush rooms, all three of which are in the 33 with no
outgoing door. The field decode and the level design agree.

**Against / unresolved.** Only two spawners fall inside 331–620 (both in room
414, spawning 0x29 Heavy Knight); the 37-sample strength comes from the whole
ROM. `unk18` is 0x100 or 0x200 in all 37 — two values — so "threshold" is a
reading of the comparison, not something the data exercises.

### 3.8 `OBJ_SMALL_CHEST` / `OBJ_BIG_CHEST` (0x80/0x81) — `unk11` is the treasure index. **High confidence.**

This one the decompilation already half-names, at
`~/Desktop/katam/include/chest.h:12-13` — `unkE0 // item id`, `unkE2 // treasure index` —
and `~/Desktop/katam/src/chest.c:30-31` assigns them straight from the record:

```c
chest2->unkE0 = arg0->subtype1;
chest2->unkE2 = arg0->unk11;
```

`unkE2` then goes to `HasChest()` (`src/chest.c:47`) and `CollectChest()`
(`src/chest.c:112`), and `unkE0` selects the reward
(`src/chest.c:114-129`: `CollectBigChest(unkE0 - 0xA)`,
`CollectSprayPaint(unkE0 - 0x14)`, `CollectMusicPlayerOrSheet(unkE0 - 0x28)`,
with `0x63` special-cased). So:

- **`unk11` on a chest = the global treasure index**
- **`subtype1` on a chest = the item id it contains**
- `unk22 & 1` on a chest inverts `ObjectBase.flags` bit 0 (`src/chest.c:33`)

The measurement that turns this from "the header says so" into a checked fact:
across all 286 rooms there are **65 small chests and 19 big chests = 84 chests,
and their 84 `unk11` values are the integers 0..83 with no repeats and no
gaps.** A perfect bijection. And 84 is exactly the chest-entry count that
`docs/naming/doors.md` arrived at from the *progress-list* side of the ROM —
two independent parses of different tables agreeing on the same number.

**Against / unresolved.** `unkF` varies on chests (10 distinct values) and I
found no chest-side reader for it; the only `Object.unkF` read anywhere in
`src/` is `~/Desktop/katam/src/lever_wall.c:15,20`, for a different type. So
`unkF` on a chest is unexplained, and I am not proposing a name for it.

### 3.9 `OBJ_DOOR` (0x6F) — `unk22` bit 8 is an art variant. **Medium confidence.**

Type 0x6F is the most-placed object in the range: 182 records across 94 of the
99 rooms (471 ROM-wide). `unk22` takes exactly two values ROM-wide — 0 (270)
and 0x100 (201) — and the only reader is a sprite-variant select:

```c
/* ~/Desktop/katam/src/mirror_door.c:120-130 (also :157, and src/special_doors.c:330,348) */
if (var)                                    variant = 8;   /* dest room 0x3D4..0x3DD */
else if (md->obj2.object->unk22 & 0x100)    variant = 9;
else                                        variant = 2;
```

So bit 8 picks a second look for the same `animId` 0x294. No other bit of
`unk22` is ever set on this type.

A free observation from the same site: the `var` branch is
`ptr->unk08 >= 0x3D4 && ptr->unk08 <= 0x3DD` — destination room **980..989**,
which is the Dark Mind end-game block (980, 981 and 982 are all in the 33 with
no outgoing door). Doors leading there get their own graphic.

**Against / unresolved.** I did not render a door with each variant to confirm
they look different, and the mapping from `unk22` bit 8 to a *visual* rather
than a *behavioural* difference rests entirely on `variant` being a sprite
field. `subtype1` on doors takes 0/1/2 (414/48/9 ROM-wide) and I did not chase
its reader.

## 4. What I could not determine

- **Whether the Moley fight in room 516 actually runs.** The room loads
  perfectly and the boss object is present, but I saw no damage to Kirby from
  two spawn points over 4,000 frames each, and a burrowing boss plus a scripted
  input of "hold RIGHT" is not a fair test. Somebody should drive this one
  properly. The same question applies to room 412, the range's third no-door
  room, which I confirmed loads but did not investigate at all.
- **Whether any of the 72 rooms in the range I did not visit behave
  differently.** 27 of 99 is a sample, and it is a sample I chose to spread
  across the extremes; a uniform result over the extremes is good evidence but
  not proof for the middle.
- **What `unkA`, `unkB` and `unkD` are for.** I established they are 0xFF in
  every one of 3,476 records and found no reader in `src/`. I did not search
  `asm/`, so "unused" is my reading and not a proof.
- **What `unkF` means on a chest**, and what `subtype1` selects on a door.
- **Whether the 143 shared `unk2==1` flag indices are intentional.** The
  measurement is solid; the interpretation is not, and it is exactly the kind
  of thing a randomizer would trip over.
- **Whether the metatile/tilemap side of these rooms is right.** The check that
  passed 27 times is the collision grid. Nothing here says the rooms *look*
  correct — `docs/ROOM-FORMAT.md` §6 still applies.
- **The pre-fix hang, kept only because the shape of it is a warning.** Against
  the pre-01:22 build, 37 of 38 warp attempts across 34 rooms hung inside the
  single frame that delivered the warp (every log stopped at
  `frameCount=1321`), and the one success was room 804 at cell (2,5) — which is
  the *only* outgoing door of room 803, the room the scripted run stands in at
  frame 1320. That coincidence is now explained by the `sub_08002C18` fix. The
  transferable lesson is that the failure mode was a hang *inside one frame*
  with no diagnostic, no log line and no crash: the port's diagnostic tally
  read 0 for a game that had stopped executing. Anything that sweeps rooms
  needs a wall-clock timeout, because the port will not tell you.
