# Room sweep, ids 621..982 — and what the object records say

**Summary.** The 621..982 range holds 82 of the game's 286 rooms. **All 82
load and all 82 reproduce their collision grids byte-for-byte** — 75,735 bytes
verified at door-arrival cells and another 25,834 verified a second time at
cell (2,5). Nothing in the range hangs and nothing is unreachable. Two rooms,
950 and 951, log a genuine diagnostic — the still-assembly
`CreateBossChallengeDoor`, isolated to 2 rooms out of 82 with room 970 as a
matched control — and the port's `port diagnostics (N)` counter reports 0 for
them anyway, which is a live trap in `tools/room_sweep.sh`'s pass criterion.

That clean result is only true of the build from 01:22 onward. The first two
thirds of this task ran against the previous binary, where 23 of my 26 sampled
rooms hung on the `PortWarp` door-table spin; those numbers are recorded as
void in §3.1 rather than as findings. Because a run now costs 3-4 seconds, I
dropped the 25-room sample and swept the whole range instead.

The static half of the task produced the durable results: **`Object.unk2`
and `Object.unk3` are a despawn-flag set selector and bit index**, verified
against all 3,476 object records in the ROM with zero exceptions and confirmed
by three independent array-size checks that land exactly; **`Object.unk4` is a
per-room register id wiring triggers to their targets**, verified by a
24-of-24 button↔door pairing across the whole ROM; **`unk1A/unk1C/unk1E/unk20`
are a rectangle** (left, top, width, height) built by the identical expression
in six unrelated source files; and **`unk5` bit 0 is "spawn regardless of the
viewport"**. Four object types' `subtype1` ranges match the exact lengths of
the four tables they index. No object type placed in this range lacks a named
constant.

Scope note: the naming section deliberately verifies against **all 286 rooms**,
not just my 82. A field's meaning is not range-local, and a claim that survives
3,476 records is worth much more than one that survives 872. Where a statement
is range-local I say so.

## 1. Method

```
python3 tools/room_export.py --rom ~/Desktop/katam/baserom.gba --room <R> --spawn
DUMP_ROOM=build/sweep-c/room-<R>.json WARP=1320:<R>:<cellX>:<cellY> \
  HOLD=0x10 MASH=600:1:6 timeout 60 \
  node tools/headless_test.js build/katam-node.js <rom> 1500 \
  > build/sweep-c/room-<R>.log 2>&1
python3 tools/room_export.py --rom <rom> --check build/sweep-c/room-<R>.json
```

Artefacts are in `build/sweep-c/`; the drivers are `build/sweep-c/run.sh`
(pass A, door-arrival cells) and `build/sweep-c/run2.sh` (pass B, cell (2,5)).
Results are `results.txt` and `results2.txt`; `results-oldbuild-void.txt` is
the void pre-fix run kept for the record.

**Coverage, and why it is not a sample.** The brief asked for ~25 stratified
rooms because a run was expected to be slow. On the fixed build the slowest of
112 runs took **4 seconds**, so a full-range sweep costs about five minutes.
I ran:

- **Pass A** — all 81 rooms that have a `--spawn` cell, warped to that cell.
- **Pass B** — 30 rooms at cell (2,5): the 26-room stratified sample (so every
  one of those was warped twice, to two different cells, and agreed both
  times), plus room 919, which has no `--spawn` cell, plus rooms 910, 913 and
  916, which no door in the game arrives at.

The stratified sample that pass B double-checks spans:

| axis | spread |
|---|---|
| songIdx (area proxy) | 0, 3, 4, 9, 10, 12, 13, 37 — 8 of the 9 present in range |
| size | 256x208 (16x13 cells) to 1936x208 (widest) and 256x1328 (tallest) |
| object count | 0 (room 969) to 30 (room 730) |

**On the 60-second timeout.** The brief suggested 300s. I measured a healthy
run before trusting anything: it reaches the warp frame in about 7 seconds
under three-way CPU contention and finishes all 1500 frames inside 15, and on
an idle machine the whole run is 3-4 seconds. A hung run spends the remaining
285 of its 300 seconds telling you nothing you did not know at second 15, so I
used `timeout 60` — still 15x the observed worst case. This is the only
deviation from the brief. It changed no result: rooms 621 and 623 were run both
ways on the old build and hung identically, and on the new build nothing gets
near the limit.

### 2.2 Diagnostics

The port's own summary counter reads `port diagnostics (0)` for **all 111
runs**. That counter is not the whole story, so I diffed the raw
`[katam-port]` output of every log instead. Three groups came out.

**Baseline, in all 111 runs, identical, and not room-specific:**

```
ROM loaded (16777216 bytes), starting AgbMain
audio: 48000 Hz, 800 samples per frame
DMA leaves the map: src=0x3FCBC034 <-- bad dest=0x0600E800 count=32 unit=2 flags=0x8000
   (x5, consecutive, then) further bad DMA transfers suppressed
warp: player 0 -> room R at cell (x,y)  /  warp: 1 delivered
```

The five bad DMA writes land around frame 840, during the attract sequence,
**before** any warp is delivered, and they appear in the passing control too.
They are a pre-existing artefact of the title sequence, not of this range.

**A real, room-specific diagnostic in exactly two rooms — 950 and 951:**

```
[katam-port] called gSpawnFuncTable1[] (ROM function table)(),
             which has no C body yet (still ARM assembly in the decomp)
```

emitted one frame after the warp lands (`platform/main.c:92`,
`PortMissingFunction`). It isolates cleanly:

- Rooms 950 and 951 are the **only two rooms in the entire ROM** that place
  `OBJ_BOSS_CHALLENGE_DOOR` (0x72), and they are exactly the two rooms that
  emit this line — 2 of 2, with 80 rooms in range as negative controls.
- `CreateBossChallengeDoor` is still assembly: `asm/boss_challenge_door.s:8`,
  `@ 0x08118B50`. It has no C body, which is precisely what the message says.
- Room **970** is the decisive control. It has the same twenty objects as room
  950 — the same mix of `OBJ_ABILITY_STATUE_1..4` — except that 950's boss
  challenge door is a plain `OBJ_DOOR` in 970. Room 970 emits nothing.
- Room 950 emits it on both passes (at cell (1,3) and again at (2,5)), so it
  is a property of the room's contents, not of the arrival cell.

The room still loads and still matches all 928 collision bytes; the missing
function is a stub call, not a crash.

**A caveat worth acting on:** `port diagnostics (0)` was printed for rooms 950
and 951 anyway. `PortError` output and the `logs` array that
`tools/headless_test.js:631` counts are different channels. That matters
because `tools/room_sweep.sh:90` decides whether a room "produced diagnostics"
by grepping `port diagnostics ([1-9]` — so **the project's own sweep would
score rooms 950 and 951 as clean.** Anything relying on that counter as the
health metric will miss every `PortMissingFunction` report in the game.

**Third group, not mine:** rooms 980, 981 and 982 also carry lines of the form
`trace star state sub_0800C558: riders, timer, kirby0Anim: ...`. That string
does not exist anywhere in this worktree's sources, so it is another agent's
in-flight instrumentation compiled into the shared binary. I record it so the
next reader is not puzzled by it; it is not a defect and it is not mine to
interpret. (Those three rooms are the 256x1280 `songIdx == 37` rooms, which is
consistent with a warp-star trace.)

## 3. What hung, and what the diagnostics were

**Nothing hangs on the current build.** That is a change of state during this
task and it is worth recording precisely, because the first two thirds of my
sweep measured the opposite.

### 3.1 What I measured on the pre-01:22 build, and why it is void

Between 01:00 and 01:22 I ran the full 25-room stratified sample plus the
control against `build/katam-node.wasm` as it stood at 00:18. **Every single
one hung.** The game reached the warp frame, the port printed
`warp: player 0 -> room R at cell (x,y)`, and the frame loop never advanced
again — same shape every time, no room-specific diagnostic, no dump written.
The raw log is preserved at `build/sweep-c/results-oldbuild-void.txt`.

The coordinator then supplied the root cause (`PortWarp` took the door branch
of `sub_080562D0`, which reaches `sub_08002C18`, whose progress-list walk at
`src/code_080023A4.c:1646` has no terminator test and spins forever when the
source room has no door to the destination) and rebuilt at **01:22:08**. Every
one of those hangs re-ran clean. **I am reporting the old numbers as void, not
as findings.**

The rebuild landed in the middle of that sweep, and the boundary is exact
enough to be worth stating, because it is the cleanest evidence I have that the
fix is the whole story:

| | |
|---|---|
| runs that **started** before 01:22:08 (old binary) | 23 — **23 hung, 0 passed** |
| runs that started after (new binary) | 3 (rooms 956, 969, 980) — **0 hung, 3 passed** |

Rooms 956, 969 and 980 look in the raw log like "three rooms that worked on the
old build". They are not: their runs began at 01:22:25 and later, after the
`.wasm` was replaced, and node reads the binary at process start. A rooms-based
reading of that data would have been wrong, and it is the reason I checked the
timestamps against the build mtime rather than trusting the file order. There
is no room-dependent component to the old behaviour at all: 23 rooms spanning 8
song ids, 208 to 1,748 collision bytes and 0 to 30 objects all failed
identically.

### 3.2 A methodological note that outlived the bug

I cut the timeout from the brief's 300s to 60s after measuring that a healthy
1500-frame run finishes in 3-15 seconds depending on CPU contention. On the
fixed build the slowest of 112 runs took **4 seconds**. A 300-second timeout on
this harness is 75x the observed worst case; it turns a five-minute full-range
sweep into a two-hour one and it buys nothing, because a run that has not
printed a new `frame NNNN:` line in ten seconds is not going to.

Concretely: sweeping all 82 rooms now costs about five minutes. There is no
longer a reason to sample.

### 3.3 No new hangs

I re-ran every room at its door-arrival cell (81 rooms) and 30 rooms a second
time at (2,5). No timeout, no non-zero exit, no missing dump, in 112 runs. If a
hang reappears it will be new.

## 4. Naming proposals, with evidence

Every claim below cites `file:line` in `~/Desktop/katam/src/` (or `wip/`) and
states what would falsify it. Counts labelled "all 286 rooms" come from a pass
over every object record in the ROM, 3,476 of them; counts labelled "in range"
cover the 872 records in rooms 621..982.

### 4.1 `Object.unk2` — despawn-flag **set selector** — HIGH

### 4.2 `Object.unk3` — despawn-flag **bit index** — HIGH

The two are always used as a pair, and never separately. The spawn loop skips
an object entirely when its flag is set:

```c
/* src/code_080023A4.c:5894 (CreateLevelObjects), and identically at
   :5950 (sub_0800A2B4) and :6010 (sub_0800A460) */
if (sub_080027E8(obj->unk2, obj->unk3, levelInfo->unk65E) != 0)
    continue;
```

and `sub_080027E8` (`src/code_080023A4.c:1426`) is a three-way bitmap read:

```c
case 0: return gUnk_02023358[roomSlot][bit / 8] >> (bit & 7) & 1;
case 1: return gUnk_02023368       [bit / 8] >> (bit & 7) & 1;
case 2: return gUnk_02028BF0       [bit / 8] >> (bit & 7) & 1;
```

The setter `sub_08001678` (`src/code_080023A4.c:688`) is the mirror image, and
**every one of its 20-odd call sites passes the same pair**, e.g.
`src/object.c:2092`, `src/object.c:2222`, `src/object_spawner.c:143`,
`src/scroll_lock.c:641`, `src/destroyable_rock_block.c:41`,
`src/star_stone_block.c:387`, `wip/large_star_stone_block.c:376`,
`wip/cutscene_trigger.c:928`. There is no call site that uses one without the
other.

So the reading is: `unk2` names **which** bitmap, `unk3` names **which bit**.
The data agrees to the letter.

| | measured, all 286 rooms |
|---|---|
| `unk2` values present | **0 and 1 only** — case 2 is never used by level data |
| `unk2 == 0` records | 3,077 |
| of those, `unk3` == running index over the `unk2 == 0` records of that room | **3,077 / 3,077, zero exceptions** |
| largest such index | **28** |
| `unk2 == 1` records | 399 |
| their `unk3` range | **0..255** |

Three independent size checks land exactly:

- `gUnk_02023358[][4]` (`include/data.h:690`) is **4 bytes = 32 bits per room
  slot**, and the per-room index never exceeds 28. It is indexed by
  `levelInfo->unk65E`, the room slot — the same index `ROOM-FORMAT.md` §3
  establishes for the collision buffer.
- `src/object.c:2224` reads `if (r6->unk3 == 31) r4->object = NULL;` — bit 31,
  the last bit of that word, is a reserved sentinel. No record in the ROM uses
  it, which is what you would expect of a reserved value.
- `gUnk_02023368[0x20]` (`include/data.h:691`) is **32 bytes = 256 bits**, and
  the `unk2 == 1` indices span **exactly 0..255**. The data saturates the array
  to its last bit.

A single mistaken address would not produce three coincidences in that
direction.

**What the two sets are for.** `unk2 == 1` is used by exactly ten types across
the ROM, and in my range they are: `OBJ_SMALL_FOOD`, `OBJ_POP_SODA`,
`OBJ_MEAT`, `OBJ_TOMATO`, `OBJ_BATTERY`, `OBJ_1UP`, `OBJ_INVINCIBLE_CANDY`
(the contiguous consumable block 0x5E..0x64), plus `OBJ_STAR_STONE_BLOCK`,
`OBJ_JACK` and `OBJ_BOSS_CHALLENGE_DOOR`. That is precisely the set whose
"already taken" state must outlive leaving the room, and `src/object.c:2082-2087`
special-cases the same consumable list when deciding whether to set the flag.
Everything else — enemies, doors, blocks — uses the per-room set, which is
cleared per room slot.

`gUnk_02023368` is cleared wholesale by `sub_080027A8`
(`src/code_080023A4.c:1417`), called from `src/warp_star.c:2685`,
`src/kirby.c:10744`, `src/code_0801C6F8.c:718`, `src/code_080332BC.c:63` and
`wip/code.c:54` — area and level transitions. That is what makes it safe for
the global indices to be reused between sub-areas, which they are (12 index
collisions in my range, all between the 700-719 and 730-744 clusters).

**Proposed names.** `unk2` -> `despawnFlagSet` (or `spawnFlagKind`);
`unk3` -> `despawnFlagBit` (or `spawnFlagIndex`).

**Against / unresolved.**
- Case 2 (`gUnk_02028BF0`, which `src/save.c:21` puts in the persistent
  `gWorldProps` buffer) is reachable from the code but **no level object in
  the retail ROM selects it**. Its meaning here is inferred from the other two
  branches, not observed.
- The names say "despawn" because a set bit *suppresses* spawning. The setter
  is also called on ordinary object *creation* (`src/object.c:2092`,
  `src/object.c:2222`, i.e. inside `InitObject`-adjacent code) — so during a
  room's lifetime the bit also means "this one is already instantiated, do not
  make a second". A name that only says "collected" would be too narrow.
- I did not observe the bitmaps at runtime. Everything above is data plus code
  reading; a watchpoint on `gUnk_02023358` during a room re-entry would close
  the last gap.

### 4.3 `Object.unk4` — trigger/target **register id** — HIGH

`sub_08002888(kind, index, roomSlot)` (`src/code_080023A4.c:1453`) returns a
`u32 *` into one of three arrays:

```c
case 0: return gUnk_02023388[roomSlot] + index;   /* u32[][16], per room slot */
case 1: return gUnk_02023488          + index;    /* u32[0x20]                */
case 2: return gUnk_02028C10          + index;    /* u32[0x20], in the save   */
```

`Object.unk4` is the `index` argument at every one of its ~30 call sites. The
decisive pair is a **writer and a reader in different files agreeing on the
same register**:

```c
/* writer — the button */
src/big_small_switch.c:302   p = sub_08002888(0, x->obj2.object->unk4, ...); *p = *p + 1;
src/big_small_switch.c:305   p = sub_08002888(0, x->obj2.object->unk4, ...); if (*p) *p = *p - 1;

/* reader — the door, and it even names the variable */
src/vert_sliding_door.c:32   open = *sub_08002888(0, door->obj2.object->unk4, ...);
```

The placement data corroborates this exactly. Across **all 286 rooms**, 24
rooms contain an `OBJ_SMALL_BUTTON` (0x6D); every one of those 24 also contains
an `OBJ_VERTICAL_SLIDING_DOOR` (0x71), and:

| | |
|---|---|
| rooms where the button `unk4` set equals the door `unk4` set | **24 / 24** |
| largest such set | room 608, ids {1,2,3,4,5}; room 426 and 911, {1,2,3} |
| both types, total placements | 35 each |

A room with five buttons and five doors, numbered 1..5 on both sides, is not
something a wrong reading produces.

The bound matches too: `gUnk_02023388[][16]` (`include/data.h:685`) has **16
registers per room slot**, and the largest `unk4` among the kind-0 users is
**15** (`OBJ_BIG_BUTTON`). Types that use kind 2 instead — `OBJ_HUB_MIRROR`
(`src/special_hub_mirror.c:71`) and `OBJ_DOOR_TO_HUB`
(`src/special_doors.c:123`) — reach 18 and 15 against a 32-entry array
(`include/data.h:703`). Nothing overflows anything.

Other kind-0 users all fall inside 16, and their reads are the same shape:
`src/lava_wall.c:50,58`, `src/cannon_fuse.c:595`, `src/jack.c:61,91`,
`src/moley.c:728`, `src/shadow_kirby.c:105`, `src/scroll_lock.c:312`,
`src/star_stone_block.c:459`.

**Proposed name.** `unk4` -> `linkId` (or `registerId` / `channel`). It is not
a boolean and not a subtype: it is the id of a shared per-room word that one
object writes and another reads.

**Against / unresolved.** Register **15** is *also* hardcoded, twice, as a
dedicated slot: `sub_08002888(0, 0xF, roomSlot)` in
`wip/large_star_stone_block.c:278` and `:325` (CPU Kirby trigger) and in
`src/big_small_switch.c:376`. Yet room 390's big button carries `unk4 == 15`.
Big buttons take a *different* branch first — `src/big_small_switch.c:71` reads
`sub_08002888(2, unk4, ...)`, the save-backed array — so the two uses may never
be live together, but I did not establish that, and it is the one place where
my reading of `unk4` has a visible tension. Do not build a level editor that
hands out register 15 freely.

### 4.4 `unk1A`, `unk1C`, `unk1E`, `unk20` — a rectangle: left, top, width, height — HIGH

Six unrelated files build the identical expression:

```c
rect[0] = (obj->base.x >> 8) + obj->object->unk1A;   /* left   */
rect[1] = (obj->base.y >> 8) + obj->object->unk1C;   /* top    */
rect[2] = rect[0] + obj->object->unk1E;              /* right  */
rect[3] = rect[1] + obj->object->unk20;              /* bottom */
```

`src/object_spawner.c:160-163`, `src/star_platform.c:42-45`,
`src/lava_wall.c:39-42`, `src/star_stone_block.c:424-427`,
`wip/large_star_stone_block.c:253-256` and `:302-305`. Offsets are in pixels
and relative to the object; `unk1A`/`unk1C` are signed, `unk1E`/`unk20` are
not, and that is exactly how they are declared (`include/data.h:270-273`).

The data is consistent with it in a way that is easy to check by eye. Room 803,
object 1: `x=1048, y=88`, rect `(-24, -88, 48, 208)`. Top becomes `88-88 = 0`
and bottom `0+208 = 208` — the room is 208 px tall, so the rectangle is the
full height of the room and 48 px wide. Rectangles that land exactly on room
boundaries are what a level designer draws; a misread field is not.

Two files use "all four zero" as "no rectangle given" —
`src/batty.c:317` and `src/golem.c:271-274` — and 797 of my range's 872 records
have `unk1E == 0`, i.e. most objects do not use the feature at all.

**Proposed names.** `rectX`, `rectY`, `rectW`, `rectH` (or
`triggerLeft/Top/Width/Height`).

**Against / unresolved.** `src/star_platform.c:26-29` adds fudge factors
(`unk1A + 8`, `unk1E - 0x10`) before using them, so a name promising an exact
hitbox would be slightly too strong; the fields are the *authored* rectangle,
which some consumers adjust. `src/shard.c:302` passes `unk1E, unk1A, unk1C` to
`sub_0805BDF4` in an order that does not look like a rectangle at all — that
one site is unexplained.

### 4.5 `Object.unk5` bit 0 — "spawn regardless of the viewport" — HIGH

```c
/* src/code_080023A4.c:5897, CreateLevelObjects */
if ((obj->unk5 & 1) == 0) {
    /* ...reject the object unless it is within ~22x17 cells of the camera... */
}
CreateObject(playerId, obj);
```

Bit clear -> the object is only created if it is near the viewport at room
load. Bit set -> it is created unconditionally.

The placements are the argument. In my range, **every** placement of these
types has the bit set: `OBJ_SMALL_BUTTON`, `OBJ_VERTICAL_SLIDING_DOOR`,
`OBJ_HUB_MIRROR`, `OBJ_BIG_BUTTON`, `OBJ_TRIGGERABLE_WALL`, `OBJ_CANNON`,
`OBJ_CANNON_FUSE`, `OBJ_WIND_EFFECT`, `OBJ_SHADOW_KIRBY`, and every boss and
mid-boss present (`OBJ_MR_FROSTY`, `OBJ_BONKERS`, `OBJ_PHAN_PHAN`,
`OBJ_BATAFIRE`, `OBJ_BOXY`, `OBJ_KING_GOLEM`, `OBJ_GOBBLER`,
`OBJ_DARK_META_KNIGHT`, `OBJ_DARK_MIND_FORM_1`,
`OBJ_DARK_MIND_FORM_3_TRIGGER`). That is exactly the set that must exist even
when off-camera — a door you open from across the room, a boss that must be
present for its fight to start — and no ordinary enemy is in it.

**Proposed name.** `unk5` bit 0 -> `SPAWN_ALWAYS` / `spawnOffscreen`.

**Against / unresolved.** Only bit 0 is read here; `unk5` is 0 or 1 in all 872
range records, so nothing constrains the other seven bits, and I found no other
reader. Five types have a *mix* of set and clear (`OBJ_OBJECT_SPAWNER`,
`OBJ_SCROLL_LOCK`, `OBJ_BIG_CHEST`, `OBJ_CUTSCENE_TRIGGER`,
`OBJ_BOSS_CHALLENGE_DOOR`) — that is expected for a per-placement flag, but it
means the reading cannot be checked by type membership alone for those five.

### 4.6 `subtype1` on the ability statues — the ability index — HIGH

```c
/* src/ability_objects.c:606-618, sub_080AA4EC */
default:                    kirbyAbility = gUnk_083538FC[object->subtype1];
case OBJ_ABILITY_STATUE_2:  kirbyAbility = gUnk_08353904[object->subtype1];
case OBJ_ABILITY_STATUE_3:  kirbyAbility = gUnk_0835390B[object->subtype1];
case OBJ_ABILITY_STATUE_4:  kirbyAbility = gUnk_0835390C[object->subtype1];
```

Those four tables are literal C arrays (`src/ability_objects.c:104-121`) of
lengths **8, 7, 1, 3**. The placement data, over all 286 rooms:

| type | table | table length | `subtype1` values observed | n |
|---|---|---|---|---|
| `OBJ_ABILITY_STATUE_1` 0x92 | `gUnk_083538FC` | 8 | **0..7, all 8 used** | 44 |
| `OBJ_ABILITY_STATUE_2` 0x93 | `gUnk_08353904` | 7 | **0..6, all 7 used** | 23 |
| `OBJ_ABILITY_STATUE_3` 0x94 | `gUnk_0835390B` | 1 | **0 only** | 8 |
| `OBJ_ABILITY_STATUE_4` 0x95 | `gUnk_0835390C` | 3 | **0..2, all 3 used** | 20 |

Four tables, four exact matches, no index out of range anywhere, and every
entry of every table exercised. `subtype1` also selects the sprite variant on
the same line (`ObjectSetFunc(arg0, arg0->object->subtype1, ...)`,
`src/ability_objects.c:605`), so the appearance and the granted ability come
from one field — as they must.

**Proposed name.** For these types, `subtype1` -> `abilitySlot` (an index into
the type's own ability table, not a `KIRBY_ABILITY_*` value directly).

**Against / unresolved.** `subtype1` is read at ~290 sites across `src/`, most
of them as a generic sprite-variant selector. **The name is type-local.** A
global rename of `subtype1` on the strength of this evidence would be wrong.

`subtype2` on the same types is a facing flag: `if (object->subtype2 != 0)
obj->base.flags |= 1;` (`src/ability_objects.c:594`), and `include/data.h:288`
documents `flags` bit 0 as "x-direction (right = 0, left = 1)". Observed
`subtype2` values are 0 and 1 only. Confidence **medium-high** — the mechanism
is unambiguous, but I did not put a statue on screen to see it face left.

### 4.7 `unk14` on `OBJ_OBJECT_SPAWNER` — packed (max alive << 8) | spawned type — HIGH

`src/object_spawner.c:63,84,92,95` and `:36`:

```c
buf = EwramMalloc((object->unk14 >> 8) * 8);            /* the alive-slot array */
if (x2->aliveCount < (object->unk14 & 0xFF00) >> 8)     /* the alive cap        */
created = CreateObjTemplateAndObj(..., (u8)object->unk14, ...)   /* the type    */
if ((u16)((u8)object->unk14 - 0x38) <= 0x1A)            /* mid-boss? use the
                                                           mid-boss SFX         */
```

All 37 object spawners in the ROM decode to a real object type in the low byte:
`OBJ_LEAP`, `OBJ_CHIP`, `OBJ_SNOOTER_1`, `OBJ_MINNY`, `OBJ_HOT_HEAD`,
`OBJ_GIANT_ROCKY`, `OBJ_BLIPPER`, `OBJ_SCARFY`, `OBJ_HEAVY_KNIGHT`,
`OBJ_PHAN_PHAN`, `OBJ_BONKERS`, `OBJ_BOXY`, `OBJ_MASTER_HAND`,
`OBJ_BOX_BOXER`, `OBJ_BOMBAR`. 37 of 37 valid — a wrong field would produce
junk indices into a 219-entry table.

The check that convinces: rooms **955, 956 and 957** — the three
`songIdx == 13` rooms in my range, each with exactly two spawners — decode to
`PHAN_PHAN`+`BONKERS`, `BOXY`+`MASTER_HAND` and `BOX_BOXER`+`BOMBAR`. Those
are the mid-boss rematch rooms, and every one of those six types falls inside
the `0x38..0x52` window that the same function special-cases for the mid-boss
sound effect.

Alongside it, from the same function:

- `unk12` = **spawn interval in frames**. `spawnCounter` is incremented per
  frame and compared against it (`src/object_spawner.c:65-66`). Values in the
  ROM: 0, 14, 24, 30, 40, 50, 60, 90, 120. Room 526's four `OBJ_LEAP` spawners
  read 60, 50, 40, 30 — a staggered cascade, which is what an interval looks
  like and is not what an id looks like. **HIGH.**
- `unk18 >> 8` = a **threshold on a level-progress counter**:
  `if (x2->unkDC >= object->unk18 >> 8)` (`src/object_spawner.c:62`), where
  `unkDC` is `gUnk_02023508[slot]` or `gUnk_02023510[slot]` depending on
  `unk22 & 2` (`src/object_spawner.c:55-58`, counters at
  `src/code_080023A4.c:1535,1545`). Values are only 1 and 2, and in each
  mid-boss room the two spawners carry 1 and 2 — i.e. first fight, then second.
  **MEDIUM**: the reading of the comparison is certain, the interpretation of
  the counter as "phase" is inference from two data points per room.
- `unk14 >> 8` (max alive) is **1 in all 37 placements**. The feature is
  implemented — there is a malloc'd slot array and a live count — and the
  shipped data never uses more than one. That is a finding, not a gap.

### 4.8 `unk11` on `OBJ_CPU_KIRBY_TRIGGER` — route-progress rank — MEDIUM-HIGH

`wip/large_star_stone_block.c:277-280` and `:324-327`:

```c
u32 *p = sub_08002888(0, 0xF, gCurLevelInfo[block->base.unk56].unk65E);
if (*p < block->object->unk11)
    *p = block->object->unk11;
block->base.flags |= 0x1000;      /* and then destroy itself */
```

The object watches the rectangle of §4.4 and, when a Kirby is inside it,
raises per-room register 15 to `unk11` — a monotone maximum, never lowered.
`src/big_small_switch.c:376` does the same to the same register.

Room **803** is the clean case: six of these, and reading them right-to-left by
`x` (1160, 1048, 816, 648, 496, 232) gives `unk11` = 60, 50, 40, 30, 20, 10.
A monotone ladder along the room's length. Across the ROM `unk11` for this type
takes only {10, 20, 30, 40, 50, 60}.

`unk22` on the same type selects **who** counts
(`wip/large_star_stone_block.c:312-315`): bit 1 -> the human players
(`i < gUnk_0203AD30`), bit 2 -> the CPU Kirbys (`i >= gUnk_0203AD30`). ROM-wide
values are 2 (16 placements), 4 (4), 6 (1) and 1 (1) — so 16 fire on the player
and 4 fire on the AI, which is what a "teach the AI the route" marker needs.

**Proposed names.** `unk11` -> `routeProgress`; register 15 ->
`REG_ROUTE_PROGRESS`.

**Against / unresolved.** I inferred "route" from the object's existing name
(`CreateCPUKirbyTrigger`) and from the ladder; I did not watch the AI Kirby
follow it. `sub_0812098C` (`wip/large_star_stone_block.c:359`) can also install
a variant that scans *objects* of type 0x79/0x7D rather than Kirbys — that
branch requires `unk22 & 1` clear **and** `unk22 & 6` set, and since bit 0 is
clear on 21 of 22 placements the Kirby-scanning variant is what actually runs.
The object-scanning variant appears to be dead in retail data.

### 4.9 `unk12` on `OBJ_SCROLL_LOCK` — camera window size in 16-px cells — HIGH

```c
/* src/scroll_lock.c:141-144, sub_0811CB44 */
p->unk8  = (object->unk14 & 0xFF00) << 4;   /* anchor x */
p->unkC  = (object->unk14 & 0x00FF) << 12;  /* anchor y */
p->unk10 = p->unk8 + ((object->unk12 & 0xFF00) << 4);   /* x max */
p->unk14 = p->unkC + ((object->unk12 & 0x00FF) << 12);  /* y max */
```

`p->unk8/unk10` become `gCurLevelInfo[].unk_S32Vec2_7C.x` and `_84.x`
(`src/scroll_lock.c:25-28`), i.e. the camera's minimum and maximum. A unit of
`<< 12` is `0x1000` = 16 px in the camera's 24.8 fixed point, so both bytes are
counts of **16-pixel cells**, high byte horizontal and low byte vertical.

47 of the 52 scroll locks in the ROM carry `unk12 == 0x0F0A` — **15 by 10
cells = 240 by 160 pixels = exactly the GBA screen**. The remainder are
`0x0F0D` (15x13), `0x0F18` (15x24) and `0x1E0A` (30x10, two screens wide).
Every value is one or two screens on at least one axis. A field that lands on
the screen dimensions in 90% of its uses is the screen dimensions.

`unk14` is the same packing for the anchor corner.

**Proposed names.** `unk12` -> `lockWidthCells | lockHeightCells` packed;
`unk14` -> `lockAnchorCell`.

**Against / unresolved.** `sub_0811CB44` is one of four setup variants selected
by `unk22 & 3` (`src/scroll_lock.c:87-107`); I read one of them closely and
skimmed the others, which use the same expression. `unk22` has further live
bits (4 and 0x10, `src/scroll_lock.c:145`, `:33`) that I did not decode.

### 4.10 `unk14` on `OBJ_BIG_BUTTON` — index into the big-switch effect table — MEDIUM-HIGH

```c
/* src/big_small_switch.c:363 */
gUnk_08357B8C[x->obj2.object->unk14]();
```

`gUnk_08357B8C` is 0x44 bytes (`data/data_13.s:15-16`) = **17 function
pointers**. There are exactly **15 big buttons in the whole ROM**, and their
`unk14` values are **1, 2, 3, ... 15 — each used exactly once**. Their `unk4`
values are also a permutation of 1..15. Two globally-unique enumerations on
fifteen objects is not a coincidence; `unk14` picks which one-shot world event
the button fires, `unk4` picks its persistence slot.

**Against / unresolved.** I did not read the 17 targets, so I cannot say what
any individual index does; index 0 and index 16 are unused by placement data.
`unk14` means something completely different on `OBJ_OBJECT_SPAWNER` (§4.7) and
`OBJ_8_DIR_CANNON` (§4.11) — this is a per-type parameter slot, not a global
field.

### 4.11 `unk14` on `OBJ_8_DIR_CANNON` — initial aim direction — MEDIUM

`src/eight_dir_cannon.c:35-40`: `cannon->unkB4 = object->unk14;` then

### 4.13 Fields that are **not** parameters

Stated because a negative result stops the next person looking. Measured over
all 3,476 object records in the ROM:

| field | value | records |
|---|---|---|
| `spawnTable` | **1** | 3,476 / 3,476 |
| `unk1` | **36** (0x24) | 3,476 / 3,476 |
| `unkA` | **255** | 3,476 / 3,476 |
| `unkB` | **255** | 3,476 / 3,476 |
| `unkD` | **255** | 3,476 / 3,476 |
| `unk16` | **0** | 3,471 / 3,476 |

- `spawnTable` is read at `src/code_080023A4.c:5979` and `:6049` as a selector
  between `gSpawnFuncTable1` and `gSpawnFuncTable2`. **`gSpawnFuncTable2` is
  never selected by level data.** Anything that permutes object records can
  leave this field alone.
- `unk1` is the walk stride, which `ROOM-FORMAT.md` §4 already establishes; the
  measurement here is that the variable-stride capability is unused — every
  record is 0x24.
- `unkA`, `unkB`, `unkD` are `0xFF` everywhere. `0xFF` reads as "absent" in
  this game's conventions (`unk10` in `RoomProps` is `-1` similarly), so these
  are three fields the level format has and the level data never fills in.
- `unk16` is zero except for **five** records, all of type 0x7C, in rooms 304,
  315 and 321 — outside my range. So it is a real parameter with exactly one
  user in the entire game.

None of these six should be given a meaningful name on the strength of level
data, because level data contains no information about them.

## 5. What I could not determine

**The dynamic sweep is now cheap and clean, which means it is also nearly
uninformative.** 82 rooms loading and matching their collision grids confirms
the room-format chain and the warp; it says nothing about whether those rooms
are *playable*. Nothing here entered a door, fought anything, or verified that
an object behaved. `docs/OBSERVING.md` §5 already says this; my results are a
large instance of it.

Specifically, I could not determine:

- **Whether any object I named actually behaves as named at runtime.** Every
  proposal in §4 rests on code reading plus placement statistics. Not one was
  checked with `DIFF=`/`symbolize_diff.py`, which is the instrument that would
  close them. The highest-value single experiment is a watchpoint or diff on
  `gUnk_02023358` across a room exit and re-entry: if §4.1/§4.2 are right, the
  per-room word for the slot should show exactly the bits of the objects that
  were killed, and it should clear when the slot is reused.
- **Whether register 15 is genuinely shared or genuinely partitioned.** §4.3
  documents a real tension — one big button carries `unk4 == 15` while
  `sub_08002888(0, 0xF, ...)` is hardcoded as the route-progress register in
  two other files. Either the big-button path never touches kind 0, or the
  retail data has a latent collision. I could not settle it from reading alone
  and it matters to anyone writing a level editor.
- **What `unkF` means.** It has five readers that disagree: a progress-counter
  comparison in `src/lever_wall.c:15,20`, and a `sub_0803DFAC(x, unkF)` call in
  three other files. It is non-zero on 81 of 3,476 records, dominated by
  `OBJ_SMALL_CHEST` (34) and `OBJ_BIG_CHEST` (15) with values up to 38, which
  smells like a chest id — but `include/data.h:264` guesses "Foreground
  boolean?" and a value of 38 is not a boolean. I have a shape, not a name.
- **`unk22` in general.** It is the most-read template field after `subtype1`
  (68 sites) and it is a per-type bitfield with no shared meaning: bit 0 is a
  rect-mode flag on the object spawner, bits 1-2 are a who-counts mask on the
  CPU Kirby trigger, bits 0-1 select one of four setup variants on the scroll
  lock, bit 8 is a sprite selector on the door. I decoded the bits I could tie
  to a specific type and left the rest.
- **`unk18` beyond the two types where I traced a consumer** (`OBJ_OBJECT_SPAWNER`
  §4.7 and `OBJ_SMALL_BUTTON`, where `src/big_small_switch.c:80` only tests it
  for non-zero). It is non-zero on 28 of my 872 range records and I did not
  chase the rest.
- **Whether the 12 duplicated global despawn indices are safe.** §4.1 shows the
  256-bit global set is reused between the 700-719 and 730-744 room clusters.
  I found the clear sites (`sub_080027A8`) and argued from them that reuse is
  safe, but I did not confirm that no two rooms sharing an index are ever live
  in the same clear-interval — and in four-player multiplayer, where four rooms
  are live at once, that is not obviously true.
- **Anything about the tilemap or tileset blobs**, which remain the real
  blocker between describing a room and rendering one.
